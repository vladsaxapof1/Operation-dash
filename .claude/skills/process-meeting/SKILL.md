# Разбор встречи

Вход: id встречи. Папка `data/meetings/<id>/` содержит `meta.json` (время, встреча
календаря с участниками) и `transcript.md` (реплики с отметками времени; спикеры —
«Спикер 1…N» или имена, если это готовая расшифровка).

## Шаги

1. **Прочитай** `meta.json` и `transcript.md` целиком.
2. **Собери контекст** (по одной команде, без конвейеров):
   - `./ops overview` — имя директора и текущие обещания;
   - `./ops people list`;
   - `./ops commitments list --brief` — все открытые задачи по строке (чтобы заметить выполненные, связать новые
     с ними и не дублировать). Полный список не вызывай — он не помещается в выдачу, увидишь только начало.
     Задачи участников встречи целиком, с «сейчас: …» — `./ops commitments list --person "<имя>"` по каждому
     участнику (кроме директора); нужна задача по теме — `--brief --search "<слово>"`, вся — `commitments show <id>`;
   - `./ops kaiten targets` и `./ops kaiten cards --limit 150` — куда создавать и что уже есть.
   - если обсуждали документ, цифры или прошлые решения — `./ops docs search "<тема>"`: сверь с презентациями
     и таблицами, в summary.md укажи файл (например, «как в «QBR Q3 2026 — Коммерция», слайд 7»).
3. **Определи, кто есть кто.**
   - **Подписанных по голосу не оспаривай.** Строка шапки «Вы в записи: <Имя> = Спикер N (…)» —
     это директор, «Узнаны: Никита = Спикер 2 (…); …» — люди из справочника; в репликах у них
     уже стоят имена. Это проверено по голосу или лично директором.
     Остальных определяй среди оставшихся спикеров.
   - **Не считай, что поручения раздаёт директор.** Директора часто зовут, чтобы поставить
     задачу именно директору. Кто есть кто — по фактам:
     обращения по имени («Дима, что у тебя?» → отвечает Дима);
     организатор встречи из `meta.json` (`event.organizer`) — обычно тот, кто позвал и ведёт;
     кто спрашивает «сколько тебе нужно / когда сделаешь» — ставит задачу,
     кто отвечает «сделаю / минут 15» — исполнитель;
     кто подробно объясняет свою часть работы — скорее всего, её и делает.
   - **Не уверен, кто из спикеров директор, — не гадай.** Пиши «Спикер 2 (вероятно, Пётр)»;
     обещания и карточки, где от этого зависит, кто исполнитель, не создавай — опиши их
     в summary.md как «нужно уточнить», а в уведомлении попроси открыть встречу и нажать
     «Это я» у своего спикера.
   - **Запиши догадку по каждому неподписанному спикеру, о котором есть факты** (кроме директора —
     своего спикера директор отмечает лично): `./ops meetings guess <id> --speaker "Спикер 3" --name "Пётр Иванов" --why "обращаются по имени [00:12:03]"`.
     Имя — как в справочнике людей. На странице встречи директор подтвердит одним нажатием, и PULSE
     запомнит голос: в следующих записях этот человек будет подписан сам.
   - Новых людей и новые написания имён добавь: `./ops people set --name "Пётр Иванов" --alias "Петя"`.
4. **Напиши `data/meetings/<id>/summary.md`** по шаблону ниже. Отметки времени `[чч:мм:сс]`
   бери из расшифровки — по ним директор найдёт место в записи.
5. **Обещания.** Каждое явное обещание с исполнителем — и каждое намерение директора с конкретным результатом
   (см. «Намерение директора — тоже задача» ниже):
   `./ops commitments add --direction mine|to_me|other --who "…" --whom "…" --title "…" --what "…" --due YYYY-MM-DD --source meeting:<id> --quote "[чч:мм:сс] дословно"`.
   `--title` — заголовок карточки, 2–6 слов («Прогноз по ключевым клиентам»); подробности — в `--what`.
   У задач директора (`mine`) — `--estimate <минуты>`: сколько времени это займёт лично у директора, а не у всего
   проекта («согласовать договор» — 30, «собрать сводку решений» — 60, «написать стратегию направления» — 240).
   Шкала: 15, 30, 60, 120, 240 (полдня); больше полдня — предложи разбить на пункты. По оценкам PULSE считает,
   хватит ли директору дня между встречами; оценку, поправленную директором лично, не меняй.
   У задач директора и «мне должны» — `--importance high|low --importance-why "<2–6 слов>"`, когда важность прозвучала:
   high — для руководителя, собственника, клиента, партнёра, про деньги, клиентов, запуск, «срочно», «критично»;
   low — «когда будет время», «не горит», мелкая административка. Обычную не указывай — её оценит навык
   `priorities`. Срок в важность не входит: его PULSE добавит сам.
   В таблице «Задачи» summary.md пиши «Что» близко к заголовку и сути обещания: по совпадению PULSE
   ставит у строки ссылку на задачу.
   - **Намерение директора — тоже задача.** Директор говорит, что сделает что-то с понятным результатом:
     «хочу / надо / сделаю / соберу / посмотрю / проверю / подготовлю» + предмет (дашборд, таблица, расчёт, выгрузка,
     документ, разбор данных). Это задача директора (`mine`), даже без слова «обещаю», без срока и без чьей-либо
     просьбы. `--whom` — тот, кому это сказано, для кого результат (собеседник; на встрече троих и больше — тот,
     о чьей работе шла речь). `--quote` — слова директора дословно. Срок — только если прозвучал: задача без срока сама
     попадёт в «Уточнить срок». Размытое — только то, где результата нет: «надо подумать про…», «интересно
     было бы…», «когда-нибудь стоит…». Его — в «Открытые вопросы», не в задачи.

     | Сказано | Что записать |
     |---|---|
     | Ольге, о её воронке: «Я хочу дашборд собрать, который будет показывать конверсию из этапа в этап. Скорость перехода из этапа в этап» | задача `mine`, `--whom "Ольга"`: «Дашборд воронки: конверсия и скорость между этапами», без срока |
     | «Давай я проверю, по какой воронке считается сделка — по созданию или по закрытию» | задача `mine`: «Проверить, по какой воронке считается сделка», без срока |
     | «Посмотрю выгрузку по отказам и вернусь с цифрами» | задача `mine`: «Цифры по отказам из выгрузки» |
     | «Надо бы подумать, как мотивировать менеджеров» | не задача — нет результата: в «Открытые вопросы» |
     | «Могу и табличку собрать, если нужно» — и никто не ответил «да, собери» | не задача — предложение без согласия: в «Открытые вопросы» («предложение директора, ответа нет») |
     | «Цель без мусорных заявок пересчитаю, если вы уверены, что менеджеры не начнут сливать лиды» — решают Пётр и Ольга | не задача, пока они не решили: в «Открытые вопросы» («решают Пётр и Ольга») |
   - **Срок в момент обещания.** Задачу директора со сроком `commitments add` сразу сверяет с окнами директора между
     встречами. Если он ответил «Срок под угрозой с самого начала … Реальнее ДД.ММ» — в summary.md допиши к этой
     задаче (в колонке «Срок» таблицы «Задачи» или после обещания в «Договорённостях»): «срок под угрозой с самого
     начала — реальнее ДД.ММ». Срок сам не меняй: реальную дату PULSE предложит директору в «Уточнить срок».
     Проверить срок до записи — `./ops day capacity --until YYYY-MM-DD --estimate <минуты>`.
   - **Можно поручить агенту.** Задачу директора (`mine`) удобно отдать агенту — Claude Code или Codex в папке
     проекта: сводка, таблица, расчёт, ресёрч, черновик, регламент, постановка, анализ — добавь
     `--agent "<что агент сделает>"` («собрать сводку KPI из выгрузки CRM»). Это только пометка на задаче:
     агента не запускай и промт не собирай — директор нажмёт «Поручить агенту» лично. Переговоры, решения,
     встречи и то, что зависит от людей, агенту не помечай.
   - **Часть другой задачи.** Если поручение — часть уже открытой задачи (Тимуру обещан
     недельный отчёт, а на этой встрече директор просит Петра собрать выгрузку) — добавь `--parent <id той задачи>`.
     Основная задача остаётся на директоре (отвечать Тимуру всё равно директору), на доске будет видно
     «Я + Пётр → Тимур». Связать уже записанную — `./ops commitments set <id> --parent <id>`.
   - **Проект.** Встреча — по делу, у которого есть активный проект (`./ops projects list`), → новые задачи
     этого дела добавляй с `--project <id>`. Новый проект сам не заводи — его предлагает навык `projects`.
   - **Ждёт.** Прозвучало, что задачу не закончить без другой («без ответов по схемам описание не отдам»)
     или до события («бюджет склада — после встречи Олега с собственником 02.11») →
     `./ops commitments wait <id> --for <id той задачи> --note "…" --source meeting:<id>` или
     `--event "встреча Олега с собственником" --until 2026-11-02`. Только по смыслу, прямо не сказано →
     `./ops propose wait --commitment <id> --for <id> --reason "…" --batch meeting:<id>`. Событие, которого ждала
     задача, случилось на этой встрече → `./ops commitments wait <id> --event "<часть текста>" --happened`.
   - **Пункты.** Обещанное состоит из названных частей (разделы, этапы, части) → после `add` —
     `./ops commitments items <id> --add "Часть 1; Часть 2"`. На встрече сказали, что часть готова, →
     `./ops commitments items <id> --done "<часть>" --note "встреча ДД.ММ [чч:мм:сс]"`.
   - **Дубли.** `commitments add` показывает похожие открытые задачи того же человека. Новая — та же работа
     другими словами или уточнение старой → `./ops commitments merge <новая> --into <старая>` и допиши
     уточнение в старую (`commitments set <id> --what/--due/--note`). Заметил дубль среди старых задач →
     `./ops propose merge --commitment <дубль> --into <основная> --reason "…" --batch meeting:<id>`.
   - **Выполнено.** Если встреча показывает, что открытая задача сделана (результат показали, прислали,
     обсуждают как готовое), — не закрывай сам, а предложи директору:
     `./ops propose done --commitment <id> --reason "<что на встрече показывает, что сделано>" --quote "[чч:мм:сс] дословно" --source meeting:<id> --batch meeting:<id>`.
     Директор подтвердит кнопкой «Да». Сам (`./ops commitments set <id> --status done --note "встреча <id>"`) —
     только если на встрече прозвучала прямая просьба директора «отметь, закрой». Выполненная подзадача ещё не значит,
     что выполнена основная: её предлагай закрыть, только если результат передан тому, кому обещан.
   - **Ход задачи.** По открытой задаче на встрече прозвучало новое (статус, договорённость, перенос, кто
     теперь делает, что мешает) — запиши шаг в её ход, по одной записи на задачу за встречу:
     `./ops commitments log <id> --text "По встрече: <что решили или сказали>" --source meeting:<id> --quote "[чч:мм:сс] дословно"`.
     Одна-две фразы, как статус: «Решили менять поставщика, Олег подпишет договор до 16.11». Это же — в раздел
     «Связь с текущими задачами» summary.md. Директор кого-то спрашивает и ждёт ответа — `--ask`.
     Договорились о новом сроке позже нынешнего («к пятнице не успеем — к 20.11») — добавь `--new-due YYYY-MM-DD`:
     срок не поменяется, директору предложат перенести. Задача встала до события («после встречи с собственником») —
     ещё `./ops commitments wait <id> --event "…" --until YYYY-MM-DD`.
   - **Задачи этой встречи.** В `meta.json` → `tasks` — задачи, которым встреча посвящена (директором они
     связаны со встречей заранее). Каждую разбери явно: договорились или сделали — `./ops propose done` (как выше);
     следующий шаг с исполнителем — новая задача с `--parent <id>`; не успели обсудить — напиши это
     в разделе «Открытые вопросы» summary.md. Ни одну не пропускай молча: что по каждой решили — ещё и в её ход
     (`commitments log`, см. выше).
5а. **База знаний и решения по темам.** Сначала посмотри темы и что по ним уже решено: `./ops decisions topics`,
   затем `./ops decisions topic "<тема>"` по темам встречи. Каждое решение из раздела «Решения» —
   `./ops kb add --kind decision --title "<суть-вывод одной строкой>" --question "<вопрос, 2–4 слова>" --answer "<что решено, коротко>" --details "почему, цифры" --date <дата встречи> --project "<тема>[ / <подтема>]" --people "Имя, Имя" --source meeting:<id> --quote "[чч:мм:сс] дословно"`
   - **Вопрос и что решено** — так директор видит решение в разделе «Решения»: вопрос — о чём решали, 2–4 слова
     («Розница: веса тимлида», «Выбор CRM»); что решено — что по вопросу действует после этого решения, до 100
     знаков, без повтора вопроса, с цифрами («35 / 12,5 / 12,5 / 40; маржа 40%»). Есть прежнее решение — вопрос
     тот же, что у него, а «что решено» — итог целиком, не одна добавка.
   - **Тема** — из уже существующих (`decisions topics`), не синоним: «KPI / Розница», а не «KPI розницы».
     Новая тема — только для нового направления работы.
   - **Цепочка.** Решение по вопросу, по которому уже есть решение, — свяжи с прежним: `--prev <id> --relation changes`
     (меняет: было одно, стало другое; прежнее перестаёт действовать), `refines` (уточняет, прежнее в силе), `follows`
     (продолжает: следующий шаг), `cancels` (отменяет). То же самое, что уже записано, — не дублируй.
     В summary.md допиши «меняет решение от ДД.ММ «…»» и упомяни в уведомлении. Статус прежней записи не трогай.
   - **Ждёт решения:** только обсудили, не решили — `--stage discussing --waiting "<следующий шаг: кто что делает или
     чего ждём>"` («Пётр посчитает эффект до 10.11», «после встречи Олега с собственником»). Принятое, но ждёт условия, —
     тоже `--waiting`.
   - Если прозвучало: `--metric "<что меняем>" --before "<было>" --after "<стало или цель>"`; задачи этой встречи,
     которые исполняют решение, — `--tasks <id>,<id>`.
   Прозвучавший урок («больше так не делаем», «ошиблись в расчёте») или удачу («это сработало, повторяем») добавь
   с `--kind lesson|win --proposed`.
5б. **Факты** — то, что пригодится директору через месяц и чего нет ни в задачах, ни в решениях: 5–15 штук, лучше
   меньше, чем мусор. Факты видны уже после чтения расшифровки, поэтому шаг не добавляет кругов: Write
   `data/meetings/<id>/facts.json` — **тем же ответом, что и summary.md** (два Write подряд в шаге 4), а
   `./ops facts import data/meetings/<id>/facts.json` — **тем же ответом, что и `./ops meetings set` в шаге 8**
   (два вызова в одном ответе). Подсказки `import` (похожий факт, похожая сущность) разбери после этого, если они есть.
   ```json
   {"source": "meeting:<id>",
    "entities": [{"name": "Ромашка", "kind": "company", "aliases": ["ООО «Ромашка»", "РМШ"]}],
    "facts": [
     {"kind": "metric", "text": "Конверсия в оплату у «Ромашки» — 12%", "key": "конверсия в оплату",
      "about": ["Ромашка"], "quote": "[00:11:37] дословно, как сказали"},
     {"kind": "trait", "text": "Олег согласует договоры только письменно", "about": ["Олег Петров"],
      "quote": "[00:20:05] …"},
     {"kind": "event", "text": "Переезд склада перенесли на март", "key": "срок переезда", "about": ["Склад"],
      "quote": "[00:31:10] …", "because": "Подрядчик по стеллажам не успевает к февралю"}]}
   ```
   - **Виды:** `metric` — цифра; `state` — состояние («новый прайс согласован»); `role` — кто за что отвечает;
     `trait` — как работает человек или клиент; `event` — что случилось или назначено, с датой; `how` — как устроено
     («выгрузка лежит в таблице …», «счёт выставляет бухгалтерия по пятницам»).
   - **Факт — одно утверждение целиком**, понятное без встречи: кто или что, и что именно. «Конверсия 12%» — плохо,
     «Конверсия в оплату у „Ромашки“ за октябрь — 12%» — хорошо. Цифры — с единицами и периодом.
   - **`about`** — о ком или о чём: имена людей как в справочнике, компании, продукты, проекты, системы. **Первым —
     тот, чей это признак** (у конверсии «Ромашки» — «Ромашка», а не Олег, который её назвал). Новую сущность опиши
     в `entities` (вид и другие написания); `import` ответит, если она похожа на уже известную.
   - **`key`** — у цифр и состояний, которые потом изменятся: имя признака, понятное без факта («конверсия в оплату
     за месяц», «срок переезда склада», «ответственный за отгрузки»), а не «стадия», «статус», «состав». Тот же ключ у
     первой сущности `about` потом сменит факт сам — «было → стало».
   - **`because`**: причина сказана прямо («перенесли, потому что …», «из-за …», «так как …», «поэтому …»). Тогда
     добавь факту поле `because` с причиной одной фразой, понятной без самого факта: кто или что, и что с ним, как
     в примере выше. `import` сам запишет причину отдельным фактом и свяжет их, в тексте факта её можно оставить.
     Причина уже записана раньше: поставь её номер, `"because": 12`. Догадку («видимо, из-за …») причиной не делай.
   - **Не факт:** задачи и договорённости (уже в шаге 5), решения (5а), оценки людей («Олег слабый»), кадровые дела
     конкретных людей (ставки, сокращения, увольнения, соглашения с HR, отпуска), биография и личное — в том числе
     самого директора, кто что сделал к встрече («Пётр собрал таблицу» — это ход задачи),
     здоровье, семья, личные деньги, пароли и ключи, болтовня, разовые происшествия без последствий и то, что верно
     день-неделю («встречу сняли из календаря»). Личная встреча (шаг 8) фактов не даёт.
   - Источник и цитата с `[чч:мм:сс]` обязательны: без цитаты факт не запишется. Сказанное как предположение
     («вроде бы», «может быть») — не факт.
6. **Карточки Kaiten.** Для конкретных поручений коллегам (и директору — если директор
   говорит «поставлю себе задачу»). Намерения директора из шага 5 («соберу», «посмотрю») — задачи в PULSE, карточку на них
   без просьбы директора не предлагай:
   - проверь дубль: `./ops kaiten cards --search "<ключевое слово>"`;
   - нет карточки → `./ops propose card --title "…" --description "…" --responsible "…" --due YYYY-MM-DD --target "…" --commitment <id обещания> --batch meeting:<id> --source meeting:<id> --reason "договорились на встрече"`;
   - карточка есть, но изменился срок/исполнитель → `./ops propose update --card <id> --due … --batch meeting:<id>`;
   - по карточке прозвучал важный статус → `./ops propose comment --card <id> --text "По встрече ДД.ММ: …" --batch meeting:<id>`.
   Если `propose` вернул ошибку про направления — не страшно: задачи останутся в
   summary.md и в обещаниях, упомяни это в уведомлении.
6а. **Текст для участников** — `data/meetings/<id>/followup.md`: готовое сообщение, которое директор
   скопирует и отправит в чат встречи. Только ключевое, простым текстом (без Markdown, таблиц и отметок времени):
   ```
   Итоги встречи «<название>» ДД.ММ

   Решили:
   • …
   Следующие шаги:
   • … (кто, когда)
   Задачи:
   • Пётр → Ольга: <что> — до ДД.ММ
   ```
   Задачи — из записанных обещаний (кто кому, срок), с настоящими именами (директора — по имени, не «я»).
   Пустые разделы убирай; 5–15 строк. Не встреча — файл не создавай.
7. **Самопроверка: открытые вопросы.** Перед уведомлением перечитай раздел «Открытые вопросы» в summary.md и
   разбери каждый пункт:
   - **Есть исполнитель и конкретный результат** (кто сделает — и что получится: дашборд, таблица, расчёт, выгрузка,
     документ, ответ) — это задача, а не вопрос, даже если срок не назвали. Уже записана на этой встрече — убери
     пункт из «Открытых вопросов»: он и так в «Задачах». Есть открытая задача раньше
     (`./ops commitments list --brief --search "<слово>"`) — перенеси пункт в «Связь с текущими задачами» и, если
     прозвучало новое, запиши ход (`commitments log`). Задачи нет — заведи её по шагу 5 (намерение директора —
     `mine` без срока) и перенеси пункт в таблицу «Задачи»; если followup.md уже написан — допиши задачу и туда.
   - **Остаётся вопросом**, только если результата нет (только обсудили), решать должен кто-то другой или
     предложение не приняли. Тогда в скобках у пункта видно, почему это не задача: «(решают Пётр и Ольга)»,
     «(предложение директора, Ольга не ответила)», «(обсудили, результата нет)».
   - Пункт о задаче этой встречи, которую не успели обсудить (шаг 5, «Задачи этой встречи»), оставь как есть.
   Если создал задачи на этом шаге — посчитай их в уведомлении вместе с остальными.
7а. **Переписка с начала встречи.** Пока встречу записывали, расшифровывали и разбирали, разбор сообщений (triage)
   уже прошёл по тому, что пришло за это время, — без задач этой встречи: их ещё не было. А «скинь в телегу» часто
   делают прямо по ходу встречи. Поэтому `commitments add` с `--source meeting:<id>` сразу показывает под новой
   задачей «По этой задаче уже писали с начала встречи» — разбери это там же, не откладывая. А когда все задачи
   записаны (шаги 5 и 7), вызови `./ops meetings messages <id>` — не раньше: до записи задач сверять не с чем.
   Это сообщения с начала встречи во всех чатах, связанных с её задачами, под каждым чатом — эти задачи
   (в том числе связанные со встречей заранее). Сверь по каждой:
   - **Прислали или сделали то, о чём договорились** (цифры, файл, ссылка, «готово, отправил») — запиши ход
     `./ops commitments log <id> --text "<что прислали — по сути, с цифрами>" --source <источник>:<id сообщения> --quote "…"`
     и предложи закрыть: `./ops propose done --commitment <id> --reason "…" --quote "…" --source <источник>:<id сообщения> --batch meeting:<id>`.
   - **Прислали не всё**, о чём просили (просили цены двух тарифов — прислали один), — только ход, и в нём видно,
     чего не хватает. Закрыть не предлагай.
   - **Задача продвинулась** (уточнили, перенесли, прислали часть, задали встречный вопрос) — только ход.
   - Не относится к задаче — пропусти.
   Что нашёл — строкой в «Связь с текущими задачами» summary.md («Цены тарифов — Пётр прислал в Telegram в 15:25,
   предложено закрыть»); предложенные закрытия посчитай в «Похоже, выполнены» уведомления (шаг 9).
8. **Сохрани итог:**
   `./ops meetings set <id> --title "<понятное название>" --headline "<главное одной строкой>" --participants "Имя, Имя" --status processed`.
   Разговор целиком личный, не о работе (здоровье, семья, поиск работы, болтовня) — добавь `--private yes`: такая
   встреча не находится поиском, не даёт фактов и не видна агентам. Задач, решений и фактов из неё не записывай,
   в summary.md — «# Личная встреча» и одна строка без подробностей.
9. **Уведоми директора:**
   `./ops notify --kind meeting --batch meeting:<id> "<b>Встреча «…» разобрана</b>\n<главное в 1–2 строках>\n\nРешений: N · задач: M · ваших договорённостей: K"`.
   Если предложено закрыть выполненные задачи — добавь «Похоже, выполнены: L — подтвердите».
   Если директору нужно что-то сделать срочно по итогам — добавь строку «⚠ …».
   Если записал догадки о спикерах — добавь строку «Проверьте, кто говорит: <a href="http://localhost:8765/meetings/<id>#who">открыть встречу</a>».

## Шаблон summary.md

```markdown
# <Название встречи>

**Дата:** ДД.ММ.ГГГГ ЧЧ:ММ · **Длительность:** N мин · **Участники:** …

## Коротко
2–4 предложения: о чём договорились и что изменилось.

## Решения
1. … [чч:мм:сс]

## Задачи
| Что | Кто | Срок | Kaiten |
|---|---|---|---|
| … | … | ДД.ММ | предложено / #id / — |

## Договорённости
- **<Директор> обещает:** … — до ДД.ММ [чч:мм:сс]
- **<Имя> обещает <директору>:** … [чч:мм:сс]

## Открытые вопросы
- … [чч:мм:сс] (кто должен решить — почему это пока не задача)

## Связь с текущими задачами
- #id «…» — что изменилось

## Кто есть кто в записи
- Спикер 1 — <Имя> (по голосу / отмечено директором / уверенно: <по каким фактам> / вероятно)
  Каждому неподписанному спикеру с именем здесь — команда `./ops meetings guess` (шаг 3).
```

Пустые разделы удаляй. Не пересказывай встречу целиком — директор хочет за минуту
понять итог. Если запись не встреча (тишина, тест, обрывок) — так и напиши в
summary.md, поставь статус processed и не создавай предложений.
